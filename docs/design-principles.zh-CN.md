# 设计原则

Agent Forge 的目标是让智能体编排和任务规模相匹配。它应该帮助 Codex 只在流程确实能提升结果时，才投入更多流程。

## 产品判断

智能体工作流需要流程预算。没有预算时，小改动容易变成昂贵仪式，而大型架构工作仍然可能缺少可持久保存的决策。Agent Forge 选择把预算显式暴露出来，而不是藏在固定流水线里。

本项目优化以下方向：

- **轻任务保持轻**：本地答案足够时，避免访谈和子代理。
- **重任务获得结构**：当歧义或失败代价较高时，使用澄清、证据、拆分和风险检查。
- **用户保留控制权**：显式参数和自然语言偏好优先于自动推断。
- **本地产物有价值**：当用户需要持久执行上下文时，确认后的计划应写入工作区。
- **低侵入优先**：除非用户明确要求，不安装 hook、不覆盖无关 skills、不修改用户配置。

## 流程预算模型

| 预算 | 典型场景 | 默认行为 |
| --- | --- | --- |
| `tiny` | 单个局部、低风险变更 | 最少上下文，无子代理。 |
| `small` | 范围窄、歧义有限的任务 | 短 grounding，只问阻塞问题。 |
| `medium` | 跨文件或跨模块规划 | 标准澄清，可选基于事实的只读探索。 |
| `large` | 架构、迁移或高风险工作 | 更深访谈、证据记录、分阶段计划，可选 critic pass。 |

这个模型不是官僚流程，而是流程上限。需求已经很详细的大任务可以快速推进；描述很粗的小任务也仍然可能需要一两个边界问题。

## 编排边界

Agent Forge 资产应能和用户已有环境组合使用：

- 优先使用 `$ralplan` 这样的显式调用，而不是隐式拦截。
- 将持久产物写入可预测的本地路径。
- 如果 Markdown 能承载同样上下文，就避免隐藏的机器专用状态。
- 用户显式启用子代理时，应广泛用于读密集探索，让主代理专注编排和综合。
- 用户未显式启用子代理时，由 agent 根据任务事实判断上下文隔离探索是否值得。
- 当当前外部事实影响正确性时，优先使用官方文档和一手来源。

## 当前实现

RalPlan 实现了这个模型的第一段：规划。它澄清模糊工作，在会话中给出草案，等待用户确认，然后写入一份 Markdown 计划文件。它刻意不执行计划、不提交变更、不做最终代码 review。

## 路线图

后续工作应保持增量：

- 只有当新 workflow skill 解决明确的用户问题时才新增。
- 执行或 review workflow 需要先明确边界，再进入实现。
- 除非多插件确有必要，否则保持单 marketplace 入口。
- 自动化应验证仓库合同，而不是增加用户 setup 成本。
